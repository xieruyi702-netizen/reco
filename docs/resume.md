## 项目经历

**Seckill — 商铺秒杀系统**

**项目简介**：Spring Boot + Redis 一主两从读写分离 + Kafka + MySQL，Docker Compose 七容器编排（Nginx 轮询负载均衡 + 双 app 实例）；两条链路：券详情查询（读，多级缓存）与优惠券秒杀（写，Lua + 异步落库）；JMeter 端到端压测验证，以下数据均为实测。

**工作**：

- **读链路多级缓存**：L1 Caffeine（5s TTL）→ L2 Redis 从库（30min）→ MySQL；自研 Redis Bitmap 布隆过滤器（Murmur3 双哈希 + 参数公式推导），启动时从从库加载本地快照、查询零网络往返，写路径 pipeline 合并；互斥锁重建防击穿、空值缓存差值化 TTL 防穿透、TTL 随机抖动防雪崩（避免同批 key 同时过期打穿 DB）。压测：直连 MySQL 2.8 万 QPS → 多级缓存 **590 万 QPS**（L1 命中主导），P99 698µs → **1µs**，10% 恶意 id 全拦截、DB 零穿透；
- **写链路高并发秒杀**：令牌桶限流（惰性补充无后台线程，50 万突发实测通过数与理论公式精确吻合，全 fail-fast）→ Redis Lua 原子判定（库存 + 一人一单一次往返）→ Kafka 异步落库削峰（纯 DB 乐观扣减 3.2 万/s → 链路化 **+146%**）；
- **最终一致性**：Outbox 本地消息表——先落账再投递，消除"Redis 已扣减但消息未发出"的崩溃窗口；落账失败整体回滚 Redis（幂等 Lua 回补）；消费端手动 commitSync + earliest 重放，INSERT IGNORE + 唯一索引幂等，重复消费不刷新截止时间；消费失败重试 3 次转死信 topic 留痕，毒消息不卡分区；混合压测逐券校验 `redis余量 + 生效订单数 = 1000` **1000/1000 全部通过，零超卖**；
- **多实例适配与状态机**：支付 CAS 流转（0 待支付 → 1 已支付/2 取消）+ Redis ZSet 延迟队列超时自动取消，Lua 幂等回补（SREM 门卫）可重新参与，支付成功主动移出队列；Nginx 轮询 + topic 双分区双实例并行消费，扫描经分布式锁互斥（锁短于周期，崩溃自动接管）；雪花算法分布式 ID（workerId 环境注入）解决双实例订单号撞号，时钟回拨拒发；券详情缓存跨实例失效——先更 DB → 删 L2 → pub/sub 广播踢 L1（至多一次，丢消息退化为 TTL 兜底），实测更新即读新值。
- **端到端验证**：JMeter 压测 Nginx → 双实例全链路 **5338 req/s 零错误**；组件级压测对照理论值验证设计正确性（限流 50 万突发通过数与令牌桶公式精确吻合）；一切数字可复现——compose 一键起环境、压测脚本与对账工具内置。
