# 面试问答话术手册

> 记录简历准备过程中的深挖问题与标准话术。按主题分组：RAG 知识库 / Outbox 一致性 / Kafka 与 ZSet / 迁移治理 / 线程池与调度。
> 使用方法：每题先背「30 秒主答案」，追问层看理解即可，不用逐字背。

## 一、RAG 知识库（social-hive 知识库条目）

### Q1：向量化是怎么做的？

**主答案**：
> "向量化本身不是难点，难的是决定**对什么文本做向量化**。我不对文档全文切块，而是给每份知识文档提炼一段 summary——比如一张表的文档，summary 就是'这张表是什么、一行代表什么、关键口径是什么、查什么问题该用它'。summary 由项目里的 GLM 按固定模板归纳，写回文档 frontmatter 固化。**对 summary 做 embedding**（调内部向量服务），存进本地 SQLite，一条向量对应一份文档，payload 带文档路径。查询时对用户需求做同样的 embedding，余弦检索 top-k，命中的是整份文档，再加载全文进 prompt。文档更新只重嵌那段 summary，成本几乎为零。"

**追问层**：
- summary 谁写的 → GLM 模板归纳 + 失败切 DeepSeek（复用已有主备降级），上线初期抽样人工校准模板，之后全自动
- 什么模型 → 内部统一向量服务（BGE 系，1024 维）；建库和查询必须同服务同版本，模型升级全库重嵌
- 为什么不切块 → 一份文档≈一张表/一个口径，天然语义完整；切块把口径切散，且召回结果不可解释
- 文档变了怎么办 → summary_hash 增量对账：变了重嵌、没变跳过、删了对账清除

### Q2：是拿用户问题向量和摘要算相似度吗？

**主答案**：
> "对。两边用**同一个 embedding 模型**转到同一向量空间：建库时 summary → 向量A 存库；查询时用户问题 → 向量B，和所有向量A 算余弦相似度取 top-k。不是字面匹配是语义匹配——'上周各档位秒挂率'和 summary 里'查接通率秒挂率用这张表'字面不同但语义相近。两道保险：建库时把表名/tags 拼进 summary 一起嵌入保证信息对等；纯语义对精确缩写不敏感，低分时叠加 tags 关键词匹配兜底。"

### Q3：top-k 怎么选取？

**主答案**：
> "k 在权衡两个失败模式：**k 太小会漏**（相关文档没进 prompt，模型只能编），**k 太大会噪**（不相关内容稀释上下文、占 token）。我的文档很紧凑（一份=一张表/一个口径），取 **k=3~5**，按 token 预算封顶。是上线初期试出来的：从 k=2 往上试，观察漏召和噪声比例，3~5 时漏召消失、噪声可控。另外加**分数下限**：top-k 里低于阈值的过滤掉，top-1 都不达标就明确说'知识库无相关内容'——**拒绝回答比编 SQL 好**。"

**追问层**：
- 检索不准怎么救 → 三层：k 调大让模型自己筛 / tags 关键词兜底 / 试跑验证兜住一切误差
- 什么时候要变 → 知识库到万级加 rerank（粗召回 20 精排 5）；文档变长改'加载摘要+按需取字段'

### Q4：向量库怎么构建的？上线后流程？

**主答案**：
> "md 文档是事实源，向量库是派生索引。系统上线后：启动全量对账一次 + 低频定时增量（10min）+ 管理端手动触发。扫描 md 目录算 summary_hash，和 SQLite 比对：新/变 → GLM 归纳 summary 写回 frontmatter → RPC 调内部向量服务 embedding → upsert SQLite（doc_id 主键幂等）；未变跳过；删除清向量。**构建是旁路任务**：GLM 和向量服务都挂也不阻塞启动和查询——沿用旧索引 + tags 关键词兜底。SQLite 随仓库发布预置索引，冷启动不用等第一轮 embedding。"

### Q5：为什么用 SQLite？md 为什么用文件不用数据库？

**主答案**：
> "SQLite 是嵌入式数据库，没有服务进程，整个库就是一个文件。几百条向量 1MB 量级，为它部署 MySQL/Milvus 是大炮打蚊子。md 用文件 + Git 管理是因为**口径修改需要 diff、review、回滚**——业务口径会被产品挑战，Git 免费送这些；分析师直接改 md 提 MR，不需要会 SQL。两者关系：**md 是人的事实源，SQLite 是机器的索引**，向量库可以随时删掉全量重建，不存在不一致难题。"

## 二、Outbox 一致性（reco 秒杀项目）

### Q6：为什么插入消息是直接写 MySQL，不交给 Kafka？

**主答案**：
> "Kafka 是传递通道不是记账本。如果依赖'发 Kafka'保证消息不丢，发送这个动作本身可能超时/崩溃，状态无从知晓。MySQL 消息表提供三样 Kafka 给不了的东西：①**持久化在发送之前完成**，落库后崩溃也有账可查；②**天然幂等**（msg_id 唯一索引 + INSERT IGNORE）；③**可查询可对账**——能扫出哪些没投出去。Kafka 负责'尽量快送达'，消息表负责'一件事只要开始了就有账'。"

### Q7：写 MySQL 消息表失败了呢？

**主答案**：
> "分三种失败：①**INSERT 失败**（DB 宕机）→ 账都没记上，这单不成立：调 LUA_ROLLBACK 幂等回滚 Redis（库存+1、移出去重集合），返回 DB_ERROR 让用户重试；②**INSERT 成功、Kafka 发送失败** → 消息已在账上，状态留 PENDING，中继每秒扫表重投，用户无感；③**进程在扣减和落账之间崩溃** → 剩余的理论窗口，工程上靠低频对账任务：比对 Redis 去重集合和订单表，发现'集合有用户但无订单'按超时处理回补库存。每一层失败要么当场回滚要么事后补偿，不存在静默吞掉的中间态。"

### Q8：消息表和订单表功能分别是什么？

**主答案**：
> "消息表是**待办清单**：记住'有一件事需要被送达'，msgId 唯一索引保幂等，status/retry 支撑中继重投，投递成功即失效，没有业务语义。订单表是**业务事实**：谁抢到了哪张券、什么状态，支付/取消的 CAS 状态机在它上面流转，一致性校验靠它数订单，长期保留。链路是：用户抢到 → 消息表记账（保证必达）→ Kafka 运账 → 订单表记实（成为业务事实）→ 消息表功成身退。消息表怕丢账（重投+幂等守），订单表怕错账（状态机+唯一索引守）。"

### Q9：既然直接写 MySQL 消息表了，为什么还要 Kafka？

**主答案**：
> "写消息表和写订单表的成本不是一个量级：消息表是单行主键顺序写，最便宜的 DB 操作；订单表是热点表，INSERT IGNORE 走唯一索引 + 库存行锁竞争。请求路径上 DB 的角色从'完成订单业务'退化成'记流水账'，真正贵的订单写入被 Kafka 挪到消费者线程按 DB 节奏慢慢做。没有 Kafka 就得轮询消息表自己当队列——延迟秒级、没有重放能力、不能水平扩展。三者分工：Lua 决定'能不能成'，消息表保证'成了必有账'，Kafka 把'账变订单'挪出用户等待时间。"

### Q10：Kafka 和 Redis ZSet 在项目里的场景？

**主答案**：
> "**Kafka 解决写入洪峰**：Redis 判定 3.2 万/秒，MySQL 只扛几千 TPS，Kafka 在中间削峰——入口快、出口由消费者控速，还送断点续传和解耦。**ZSet 解决未来某时刻的动作**：待支付订单 ZADD 进延迟队列（score=支付截止时间戳），定时任务 ZRANGEBYSCORE 0 now 一次取出全部到期订单，到期前零成本，不用轮询每个订单或慢查询扫表。一个管'到不到'，一个管'什么时候收尾'。"

### Q11：Kafka 生产者的逻辑？

**主答案**：
> "配置上 acks=all + enable.idempotence（等所有 ISR 副本落盘 + broker 端去重），linger.ms=5 批量。主链路 Outbox 三步：①先落消息表（失败→回滚 Redis 拒单）；②同步 send().get(2s)；③成功 markSent。②③失败内部吞掉留 PENDING 给中继补投，用户拿 SUCCESS 是成立的因为账在。补偿链路：LocalMessageRelay 每秒扫 PENDING（retry<10）重投，复用同一 Producer 同一消息，重复靠消费端唯一索引吃掉。**Producer 的可靠发送管'快'，消息表管'一定'，PENDING 状态衔接两段。**"

### Q5.5：明明有相关文档，但相似度算错了检索不到，怎么办？

**主答案**：
> "先定位原因——'该中没中'通常三种：①query 和 summary 说法差太远（用户写'拉新转化'，summary 写'注册渠道分析'）；②embedding 对内部黑话/缩写不敏感；③摘要本身没写到位。三道防线按成本从低到高："

- **① 混合检索（最有效）**：向量一路 + 关键词一路（分词匹配 frontmatter 的 title/tags/表名，SQLite FTS5 即可）取并集——向量管语义相近，关键词管精确命中（'vm_di' 这种缩写向量认不出来，关键词直接救回）；
- **② query 改写 + 调 k**：检索前让 LLM 把口语需求改写成含标准术语的检索友好形式再 embed；top-k 取大（5→10），文档短 token 装得下，边界情况放进去让模型自己筛；
- **③ badcase 回流改数据（治本）**：每个'该中没中'的查询，把用户实际说法补进对应文档的 summary/tags 当同义触发词——**检索调优的终局是改数据不是改算法**，闭环跑起来同类 badcase 只犯一次。

**加分收尾**：
> "上线前拿真实需求建小评测集：每条标注期望命中的文档，改完跑命中率——**没有评测集的检索调优都是玄学**。规模到万级再考虑加 rerank 精排，当前规模简单方案是最优解。"

**记忆骨架**：先分类原因（说法差/黑话/摘要差）→ 关键词并集兜精确 → query 改写兜语义 → badcase 回流改 summary → 评测集验证。

## 三、迁移治理（user-commlzn-reco）

### Q12：怎么理解"老系统迁移过来所以有很多缺陷"？

**主答案**：
> "迁移的目标是'行为对等、快速切换'，不是'顺便重构'——因为一旦新旧系统行为有差异，灰度比对就没法做了。所以旧代码的历史债（setnx 锁、漏掉的清理逻辑）被原样搬进新系统，这是**故意先不修**的。代码里的痕迹：OLD_MATCH_LOCK_REDIS/MATCH_LOCK_REDIS 双集群并存、贯穿所有 DAO 的 matchVersion、DualJedisFactory 双 Redis 路由，都是迁移期灰度回滚的基建。切换完成后这些债成了没人认领的雷——这就是 mentor 说还有很多缺陷的原因，也是'我负责模块梳理、修复锁缺陷'这个故事的完整背景。"

### Q13：分布式锁缺陷怎么发现的、怎么修的？（最强故事）

**主答案**：
> "这个服务是从老匹配系统迁移过来的，迁移策略行为对等优先，旧写法被原样带过来。我梳理延迟队列模块时发现 super match 的分布式锁是 setnx 之后**单独** expire——两步之间进程崩溃，锁就永久泄漏，这个用户永远匹配不上。修法：改成 SET NX EX 一条命令原子完成，释放时校验锁的 value 归属防止误删别人的锁。同模块还发现消费侧其实已经是 Lua 原子弹出（ZRANGEBYSCORE+ZREM 一次往返，还处理了同分任务误删），**消费侧是原子的、加锁侧不是**——这种并发治理水平不一致正是迁移遗留的典型形态，我负责把整个模块拉齐。"

**追问层**：
- setnx 后进程没崩但 expire 前异常呢 → 同样泄漏，所以必须原子命令；集群下主从切换也可能丢锁，强一致场景要 Redlock 或接受"锁只是优化不是正确性保证"
- 锁到期业务没跑完 → 看门狗续期（后台线程定期 expire）；业务要保证幂等，锁过期被抢走也不会双写

## 四、线程池与调度（social-hive / user-commlzn-reco）

### Q14：线程池怎么设计的？拒绝策略为什么这么选？

**主答案**：
> "按职责分池：跑批执行池用 AbortPolicy——池满说明下游（Hive 平台/用户提交）过载，快速失败保护；SQL 队列池用 CallerRunsPolicy——SQL 丢一条的代价远大于让提交线程顺手执行一条，所以背压而不是拒绝。**拒绝策略跟着'丢这个任务的代价'走，不是跟着口味走。**"

### Q15：动态定时调度怎么做的？比 @Scheduled 好在哪？

**主答案**：
> "@Scheduled cron 写死要发版；DB 轮询方案有空转和延迟。我的实现：cron 存 MySQL，ThreadPoolTaskScheduler + CronTrigger 动态注册——页面改周期 → 存库 → cancel 旧 future 按新 CronTrigger 重注册，立即生效。firing 并发集合防同任务重入；重启 catch-up：next_run_at 已过期立即补跑，错过的周期不丢。为什么不用 xxl-job：内部工具、几十个任务、单实例，引调度中心是多余的依赖；多实例才需要分布式锁或分片，那个规模 xxl-job 才划算——**选型跟着规模走**。"

### Q16：延迟队列消费为什么批量弹出后用独立线程池并发处理？

**主答案**:
> "三三百毫秒批量弹出到期任务，逐条 CompletableFuture 提交独立业务线程池并发 recommend。为什么调度线程和消费线程分开：@Scheduled 默认单线程，recommend 是慢 RPC，共用会拖死调度周期。批量和开关收 Apollo，线上可调可止血。"

## 六、压力测试题

### Q17：为什么这个系统有这么多技术漏洞？

**主答案**（把漏洞归因到结构性原因，落到自己的贡献）：
> "这些漏洞不是同一批性质，分三类：**①迁移遗留债**——链路从老系统迁来，迁移约束是行为对等（灰度比对的前提），所以照搬不重构，旧问题被有意带进来；setnx 锁在老系统单实例下没暴露，新服务多实例并发下窗口被放大。**②平台角色升级**——调试平台早期丢调试数据不致命，被越来越多人依赖后可靠性标准升级，pause/resume 改造本质是标准跟着角色走。**③规模演进残留**——串行批量查询量小时没问题，量上来 P99 就撑不住。我做的就是迁移完成后的治理期工作，而且是按模块系统性治理——修锁顺手把同模块消费原子性拉齐，不是打地鼠。"

**红线**：绝不说"原代码写得太烂"——前同事可能就是面试官的团队。

### Q18：这些指标是怎么评估计算的？

**主答案**（每个数字给测量方法 + 口径 + 局限性）：
> "个人项目有内置压测框架（三模式 + CountDownLatch 多线程），数字分两类：**性能类**——590 万 QPS / P99 1µs 是 L1 本地内存命中的物理量级，意义是证明热 key 不走网络的设计生效，不是'系统能扛 590 万'；**正确性类**——零超卖/1000/1000 是对账恒等式（redis余量+订单数=1000 逐券校验），限流 361 与令牌桶数学吻合，这些是设计正确性验证。实习场景拿不到独立压测环境：P99 从线上监控打点读优化前后稳定窗口对比，**不编百分比就说'显著下降'**（没做严格 A/B 隔离是事实）；-89% 有明确口径——同一批任务改前人工流程 vs 改后自动化的墙钟时间对比，分母是纯人工所以数字大是合理的；RPC 降量级从缓存命中率 95%+ 推导。"

**记忆骨架**：个人项目 = 压测工具 + 对账恒等式，可复现；实习 = 线上监控读数 + 明确口径 + 主动承认局限性。**数字完美反而不可信。**

## 八、串场与组合话术

### 自我介绍版（Soul 实习一段话）

> "实习期间主要做 Soul 语音匹配服务的后端迭代与治理：一条线是在线链路优化——分析了执行计划发现并行化率低，把高耗时的算子组改成并行编排，链路耗时降了约 100ms；另一条线是这条链路从老系统迁移过来的遗留治理，修了一个会永久泄漏的分布式锁。另外我开发了一个实验策略取数 Agent：在跑批平台之上建了两套知识库，让 AI 按自然语言需求自己查口径、生成 SQL、直查 Hive 验证。"

### 拒答与边界（防止吹爆）

- 营收 +3% 是产品目标 → "还在实验灰度，我负责的链路已上线"
- pipeline/DAG 框架 → "基于团队的框架做算子开发和优化"，不 claim 框架设计权
- 知识库 → 真实规模几百份文档，主动讲"SQLite 够用、选型跟规模走"，不吹分布式
