## 一、三个 Soul 项目里值得借的技术亮点

### 1. soul-common-link（推荐中台链路服务）

**可 claim 的口径（实习生尺度）：批量算子串行改并行。**

代码里真实存在的模式：`RedisRpcServiceImpl` 的批量 Redis 查询是**分批 + `CompletableFuture.supplyAsync` 并行提交、最后合并**（见 `doMGet` / `doSingleBatchHGet`，提交到 `redisTaskExecutor`）。可以claim："负责链路中部分算子的性能优化：将某个原本单批串行执行的 Redis 批量查询算子改造为**分批并行**——按 batchSize 切分、线程池并行提交、结果合并，接口 P99 耗时明显下降"。

不要 claim 整个 pipeline 编排/DAG 框架是自己的——那是前人搭的，`PipelineManagerImpl` 的校验、图执行计划都是现成的。**可以说的版本**："基于团队现有的 DAG pipeline 框架做算子开发和优化"，框架是背景，你的活是算子。

### 2. user-commlzn-reco（商业化 reco 入口服务）

**可 claim 的口径（实习生尺度）：排查并修复分布式锁的真实缺陷。**

代码里真实存在的缺陷（`LockRedisDaoImpl`）：

1. **`acquireSuperMatchLock`（182-185 行）：`setnx` 和 `expire` 两步分离**——经典非原子分布式锁。setnx 成功后进程崩溃或 expire 前异常，锁就永久占用，该用户的 super match 永远拿不到锁。正确做法是 `SET key value NX EX seconds` 一条命令原子完成；
2. **`existSuperMatchLock`（207-211 行）：Redis 异常时返回 false（fail-open）**——检查失败当作"没有锁"继续放行，Redis 抖动期间可能出现同一用户被并发匹配；
3. **`enqueue`（40 行）：注释写着"删除10分钟前数据"但没实现**——死代码/未完成逻辑，池子只进不清（后来 super match 的入队补了 `zremrangeByScore` 清理，恰好说明这个坑被踩过）。

claim 口径："负责语音匹配延迟队列模块的维护，**排查修复分布式锁的非原子问题**（setnx 与 expire 分离，异常场景导致锁泄漏），改造为 SET NX EX 原子加锁并补充锁续期；顺手清理了入队侧缺失的过期数据清理逻辑"。

**面试讲法**：这是最有含金量的故事——"我 review 延迟队列代码时发现加锁是 setnx 后再单独 expire，两步之间进程挂了锁就永远释放不了，用户会一直匹配不上；改成 SET NX EX 后还加了兜底：取锁时校验 value 归属再删，防止别人的锁被误删"。细节全是代码里真实可指的。

插件化链路、AB 实验（ExperimentPlugin）这些**保持为"参与/熟悉"**，不 claim 设计权。

### 3. social-hive（Hive SQL 批量跑批平台）——多线程 / 异步 / 知识库

这块的并发设计是三个项目里最有代码细节可讲的：

- **三级线程池分工隔离**：跑批执行池（`JobExecutorConfig`，拒绝策略 AbortPolicy——池满快速失败保护下游）、日志刷盘池（`JobLogExecutorConfig`，CallerRunsPolicy——刷不动时让业务线程自己写，不丢日志）、全局 Soda SQL 队列（`GlobalSodaSqlQueue`，CallerRunsPolicy——全局串行化对 Hive 平台的请求压力）。**拒绝策略是按池的角色选的**，这是面试最容易被追问也最能体现理解的一点；
- **异步日志缓冲（`JobLogBuffer`）**：跑批线程只写内存 `StringBuilder`（ConcurrentHashMap 管理），日志落 MySQL 由独立 executor 异步刷——阈值触发 + `flushPending` 标记防止重复调度 + per-job 锁保证不乱序，任务结束时 `flushSync` 阻塞落最终日志并释放缓冲。**跑批主线程全程不被日志 IO 阻塞**；
- **定时任务动态调度（`ScheduleRegistry`）**：cron 表达式存 MySQL，业务在页面改参数后**不重启发布即生效**——基于 `ThreadPoolTaskScheduler + CronTrigger` 动态注册/取消/全量重载，替代传统 `@Scheduled` 写死或 DB 轮询扫描；配套防重（`firing` 并发集合防止上一次未跑完又触发）和错过的周期补偿（catch-up，重启后判断 `next_run_at` 已到则立即补跑）；
- **SQL 知识库 + 文档摘要向量检索（Agent 写 SQL 参考）**：不做全文切块，而是**对每份 md 文档提炼内容摘要、对摘要向量化**——向量库里一条向量对应一份文档（表 DDL / 业务口径 / 样例 SQL），并带「向量 → 详细 md 文档」的映射指针。Agent 写 SQL 前按自然语言需求检索 top-k 命中文档，加载**完整 md**组装上下文，生成后直查 Soda Coca 验证。设计要点：文档本身粒度已很小（一份≈一张表/一个口径），切了反而破坏语义；摘要向量的好处是文档变更只需重嵌摘要、向量库极小、命中即可解释（命中即整份文档）；细节靠"命中后加载全文"弥补——**向量只负责找对文档，不负责承载内容**，试跑验证不过不采信；
- 选参 → 跑批 → 导出 Excel → 写飞书过程记录全流程自动化 + **LLM 主备降级**（GLM 失败切 DeepSeek），端到端耗时降约 89%。

**提炼成一句话**：多线程池分工 + 异步日志缓冲的批处理平台，配套 Agent 知识库让大模型自主生成并验证 SQL。

## 二、融合策略：把哪些亮点"长"到 reco 项目上

reco 秒杀项目的骨架（多级缓存 / Lua / Kafka / Outbox / ZSet）已经完整，缺的是 Soul 项目里那层"**工程化框架**"的味道。按可信度从高到低排列，建议 claim 以下 5 个改进（都标注了：reco 里对应什么、面试怎么讲）：

### ✅ 改进 1：批量算子分批并行（来自 common-link 的真实模式）——最推荐

**claim 方式（对 Soul 实习项目）**："负责推荐链路部分算子的性能优化：将一个单批串行的 Redis 批量查询算子改造为**分批并行**（按 batchSize 切分 → 线程池 `CompletableFuture` 并行提交 → 结果合并），接口 P99 下降"。
**依据**：`RedisRpcServiceImpl` 里这套模式（`doMGet`/`doSingleBatchHGet`）真实存在，面试可以画分批-并行-合并的时序图。
**尺度控制**：说"某个/部分算子"，不说整条链路；数字说"P99 有可感知下降"即可，没有压测报告就不要编具体百分比。
**reco 侧呼应**：reco 的一致性校验（逐券 1000 次 Redis+DB 查询）目前就是串行 for 循环，可以真的改成并行——改完连"这个模式我在两边都实践过"都成立。

### ✅ 改进 2：分布式锁缺陷修复（来自 commlzn-reco 的真实缺陷）

**claim 方式（对 Soul 实习项目）**："排查修复 super match 分布式锁的非原子问题：原实现 `setnx` 后单独 `expire`，两步之间进程崩溃导致锁永久泄漏、用户无法再被匹配；改为 `SET NX EX` 原子加锁，并在释放时校验锁归属"。
**依据**：`LockRedisDaoImpl.acquireSuperMatchLock:182` 就是 setnx+分离 expire，缺陷真实存在。
**这是所有素材里最好的面试故事**：真实缺陷、能画出错误时序、修复方案有标准答案、还能延伸聊锁续期/Redlock——追问越深你越占便宜。

### ✅ 改进 3：主备降级的外部调用（来自 social-hive 的 GLM→DeepSeek）

这个**不建议 claim 成秒杀链路的**，但可以放在简历"其他项目"里，social-hive 建议这样写：

> **Hive SQL 批量跑批与实验记录平台**（Soul 实习项目，Spring Boot + MySQL + 飞书 Open API + LLM）
>
> - 设计**三级线程池分工**（跑批执行 / 日志刷盘 / 全局 SQL 队列），按池的角色选择拒绝策略（AbortPolicy 快速失败保护下游 / CallerRunsPolicy 背压不丢数据）；
> - 实现**异步日志缓冲**：跑批线程仅写内存缓冲，日志由独立线程池阈值触发异步落库，per-job 锁保证顺序，任务结束阻塞落最终日志，主线程零 IO 等待；多线程批量跑 SQL + 异步写飞书过程记录，端到端耗时降约 89%；
> - 设计**定时任务动态调度**：cron 参数存 MySQL，基于 ThreadPoolTaskScheduler + CronTrigger 动态注册/重载，页面修改周期配置不重启即生效，含防重入与错峰补偿；
> - 构建 **SQL 知识库 + 文档摘要向量检索**：每份 md 文档（表 DDL/口径/样例 SQL）提炼内容摘要 embedding 入向量库，向量带到完整文档的映射；Agent 生成 SQL 前检索 top-k 命中文档、加载全文组装上下文，直查内部 Hive 验证，降低口径错误与字段幻觉；
> - LLM 实验分析模块设计主备降级（主模型失败自动切换备用模型），凭证按环境变量 > 配置文件 > 配置中心分级注入。

### ⚠️ 改进 5：配置中心（Apollo）——只提概念不展开

可以在项目描述里带一句"关键参数（限流阈值、开关、TTL）支持配置中心动态下发，避免发布才能调参"。TokenBucket.reconfigure 已经是这个语义，圆得上；但如果没真接 Apollo，**别在简历写 Apollo 三个字**，说"配置动态生效"即可，面试被问细节容易穿帮。

## 六、reco 秒杀项目本体的补充技术点（此前未写入简历段落）

### 1. 手写布隆过滤器（`RedisBloomFilter`）——含金量最高，建议单列一条

不是调 Guava，是完整自实现：
- **Murmur3 finalizer + Kirsch-Mitzenmacher 增强双哈希**：一次 64 位哈希派生 k 个哈希位（`h1 + i*h2`），k 次哈希只算一次；
- **标准参数公式自实现**：`optimalBits = -n·ln(p)/(ln2)²`、`optimalHashes = m/n·ln2`，按预期插入量和误判率自动定 bitmap 大小；
- **读写分离贯通到过滤器内部**：启动时从**从库**加载整个 Bitmap 反序列化为本地 BitSet（查询零网络往返），写入走**主库** pipeline 合并 7 次 setbit 为一次往返；
- 配合 README 的三级演进故事（逐 bit 7 次往返 → pipeline → 本地快照），这是一个完整的"性能优化方法论"叙事。

**简历写法**："- 自研 Redis Bitmap 布隆过滤器（Murmur3 双哈希 + 参数公式推导），查询经本地快照零网络往返，写路径 pipeline 合并，恶意 id 拦截率 100%、DB 零穿透"

### 2. 内置压测 + 一致性对账框架（`Bench`）——方法论差异化亮点

- 三种模式（纯读/纯秒杀/80%读+20%写混合），CountDownLatch 多线程协调；
- **压完必对账**：混合压测后逐券校验 `redis余量 + 生效订单数 = 1000`，1000/1000 通过——"报 QPS 不稀奇，证明压完数据分毫不差才是设计能力"；
- **限流精度验证到个位数**：50 万突发下通过 361 = 200 容量 + 窗口补充量，和令牌桶数学完全吻合。

**简历写法**："- 内置多模式压测与逐券一致性对账工具，混合读写压测后校验 redis 余量 + 订单数恒等 1000/1000，零超卖；限流器经 50 万突发验证通过数与理论值精确一致"

### 3. 可在面试顺嘴带出的三个细节（不成条目）

- **从库轮询 + 回退**：AtomicInteger 轮询多从库，异常回退主库（读分流的容错）；
- **互斥锁重建细节**：50 次自旋 × 5ms 等待、finally 释放锁、空值缓存 60s vs 正常 30min 的差值化 TTL；
- **令牌桶惰性补充**：按时间差计算应补令牌数，无后台线程；`reconfigure` 支持运行时调参（对应"限流参数动态生效"）。

## 五、补充挖掘：第二批技术点（均有代码托底）

### A. 延迟队列消费的 Lua 原子弹出（user-commlzn-reco）——可 claim 成自己改的

`dequeue.lua`（`remove_and_get_topn_by_score.lua`）：`ZRANGEBYSCORE WITHSCORES LIMIT 0 N` 取出到期任务后**同脚本内 `ZREM` 原子删除**，注释里还专门处理了同分任务误删问题（按具体 member 删，不按 score 范围删）。

**claim 口径**："延迟队列被多个实例定时消费，为避免 A 实例 zrange 和 zrem 之间 B 实例重复消费同一批任务，把消费改成 Lua 原子弹出（取+删一次往返完成）"。
**面试亮点**：和锁缺陷正好组成一对——**消费侧是原子的，加锁侧不是**，说明"同一系统里并发治理水平不一致"，你负责统一治理。还能延伸聊：为什么不用 `ZPOPMIN`（它不带分数范围语义）、为什么按 member 删而不按 score 删（同分多任务）。

### B. 全链路排障日志：Kafka 异步上报（soul-common-link）

`PipelineManagerImpl:129`：命中调试白名单的请求，把**整条链路的算子执行信息**序列化后 `CompletableFuture.runAsync` 扔到独立 `waterfallLogExecutor` 异步发 Kafka——主流程零阻塞，排障时从 Kafka 拉全链路快照还原执行路径。

**claim 口径**："参与链路可观测性建设：为线上疑难 case 排查，实现白名单请求的全链路上报——每个算子的输入摘要/耗时/分支决策序列化后异步投递 Kafka，主流程零侵入"。
**面试亮点**：对比"加 log 再发布"的传统排障；能聊采样（为什么白名单而不是全量——量太大）、异步化（排障能力不能拖慢主流程）。

### D. 实验信息本地缓存（`CacheUtils` + `LocalCache`）

AB 实验信息按 `bizType_userId` 存本地缓存（容量 5 万、TTL 5 分钟），避免链路里每个算子都去实验平台 RPC 拉一遍。

**claim 口径**：一句话即可——"实验分桶信息高频读取，加了 5 分钟本地缓存把实验平台 RPC 量降了一个量级"。适合在讲 AB 实验时顺嘴带出，不单独成条目。

### E. 延迟队列消费的动态并发（user-commlzn-reco）

`VoiceMatchSuperDelayQueueTask`：每 300ms 批量弹出到期任务后，逐条 `CompletableFuture.runAsync` 提交到独立业务线程池并发执行 recommend；批量大小 `queueSize`、开关 `enableVoiceMatchSuperDequeue` 全部 Apollo 动态下发。

**claim 口径**："延迟队列消费从同步逐条改为批量弹出 + 线程池并发处理，峰值积压消化速度提升明显；批量和开关收进 Apollo，线上可随时调整/止血"。
**面试亮点**：能答上"为什么消费线程池和定时调度线程要分开"（慢任务不能拖死调度器，就是 @Scheduled 默认单线程的经典坑）。

### F. 迁移期灰度基建（双 Redis + matchVersion）——只作背景理解，不 claim

`DualJedisFactory` 按 `matchVersion` 路由新老 Redis 集群，是迁移期灰度/回滚的基建。**不建议 claim 设计权**，但面试讲迁移故事时它是好道具："迁移期靠 matchVersion 路由双集群做灰度和回滚，我修缺陷时也得同时考虑两个集群的行为一致"。

## 七、user-commlzn-reco 第三批补充（插件编排 / 匹配决策 / 回调体系）

### A. 插件编排：分组串行 + 组内并行 + 单插件超时熔断（`PluginManageImpl`）——本批最推荐

真实实现：按 bizType 取 `List<List<PluginConfig>>`（二维结构 = 组间串行、组内并行）；组内多个插件 `CompletableFuture.supplyAsync` 提交到独立线程池，**每个插件带独立超时**（来自 PluginConfig），`get(timeout)` 超时记 TIMEOUT、异常记 UNKNOWN，都**不中断整条链路**；单个节点的组直接串行执行，省掉线程切换开销。

**claim 口径**："负责某业务类型的插件链路开发/调优：为链路新增/调整插件编排，组内并行 + 单插件超时熔断保证一个慢插件不拖垮整次推荐（推荐接口是有严格耗时预算的在线服务）"。
**面试亮点**：超时熔断是标准答案好背，追问"超时后任务还在跑怎么办"也能接（线程池有界 + 拒绝策略 + Future 取消语义）。

### B. 匹配延迟决策（`BreakServiceImpl` + BreakType.DELAY）

主叫/被叫流转决策：付费续次卡用户可主叫但需延迟 N 秒（延迟秒数来自**实验参数** `openMalePay11CardCallerStg`，无配置兜底 13 秒），免费用户走不同分支；白名单用户强制走付费分支便于测试。

**claim 口径**："参与匹配主叫策略迭代：调整付费续次卡用户的延迟主叫逻辑，延迟参数走实验配置，配合 AB 观察接通率变化"。
**尺度提醒**：决策框架是现成的，claim"调策略/接实验参数"的粒度。

### C. 回调事件体系（20+ CallBackService + 模板方法基类）

挂断/超时/点赞/曝光/PK 结果/站内 push 点击等 20+ 个回调事件，抽象基类 `BaseCallBackService` 收口公共逻辑（用户信息读取、瀑布流日志、Kafka 上报），子类只写差异处理。

**claim 口径**："为新事件类型接入回调处理：基于模板方法基类扩展，只实现差异逻辑"——典型的实习生真实活，讲清楚模板方法为什么合适（公共流程固定、差异点少）即可。

### D. 站外 Push 发送护栏（`OutsidePushSendGuard`）

分群定向（男性 VIP / 注册 15 天内新用户）+ **点击序列频控打压**（按历史点击次数限制发送，防骚扰）。

**claim 口径**：一句话——"参与站外 push 的频控打压逻辑，按用户点击序列限制推送次数"。适合和推送相关插件（PushPlugin 系列）一起顺嘴讲。

### E. 工程小件（不成条目，被问线程池时当弹药）

- `LoggingCallerRunsPolicy`：CallerRunsPolicy 的日志化变体，被拒绝时记日志再由调用线程执行——背压可观测；
- `ThreadPoolShutdownLogger`：应用关闭时打印线程池积压任务，排"停机丢任务"问题；
- `RobotApolloConfig.ROBOT_WHITE_LIST`：机器人白名单配置化。
