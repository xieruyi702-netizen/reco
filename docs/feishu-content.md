## 一、实习经历：Soul 语音匹配服务

### 1.1 背景：我负责的是什么

语音匹配是 Soul 的核心玩法之一：用户发起匹配，系统从候选池召回、过滤、排序后推送对方。这条链路由多个服务组成——common-link 负责算子 pipeline 执行，commlzn-reco 负责商业化插件编排，配套延迟队列（超时未接通的匹配流转）、分布式锁（匹配双方互斥）等基础设施。这条链路从老系统迁移而来，迁移约束是行为对等（新旧系统灰度比对的前提），因此旧代码的历史问题被原样带入新环境。我的工作分两条线：在线链路的性能与可靠性优化，以及迁移完成后回头偿还的历史债。

---

### 1.2 定位卡等待弹窗推荐

#### 背景与问题

定位卡（cardType=8）用户的匹配成功率低于其他功能卡——他们用卡发起匹配后，如果一直等系统自然匹配，接通率会随等待时间下降。业务做法是：等待超过阈值（25 秒，Apollo 可配）仍无结果时，主动向等待用户弹窗推荐候选女性，把"干等"变成"给一个可接起的选项"。

#### 技术方案

触发与排队：达到阈值时任务写入 Redis ZSet 延迟队列（score = 到期时间戳），由多实例定时任务消费。消费采用 Lua 脚本原子弹出——ZRANGEBYSCORE + ZREM 在 Redis 单线程内一次往返完成，规避多实例重复消费；按具体 member 删除而非按分数范围删除，规避同分任务误删。候选匹配：采用 Redis 分布式锁锁定双方——SET NX EX 原子加锁杜绝"加锁成功但未设过期"的锁泄漏，释放时 Lua 脚本校验锁归属（是自己的锁才 DEL）防误删。频控：弹窗发送（card_pop_sent）与曝光（card_pop_expose）双 Redis key 由 reco 写、link pipeline 前置读，实现主叫拦截与候选过滤——同一用户不会被反复弹窗。准入条件与等待阈值全量 Apollo 动态下发。

#### 常见追问

ZSet 为什么不用 Kafka 延迟：弹窗触发是固定时长语义（score 即截止时间），ZSet 的按分数范围取数天然匹配，且任务暂停不丢失。锁为什么不用 Redisson：锁是秒级互斥优化不是资金安全，原生 SET NX EX + Lua 释放足够，少一个依赖。

### 1.3 免费男性延迟匹配 UCB 策略支撑

#### 背景与问题

免费男性发起匹配后立即推送接通率低，业务策略是延迟一段时间再匹配。延迟多久是两难：短了候选少质量差，长了用户流失，且不同付费等级用户耐心不同。建模为多臂老虎机：延迟档位离散成 7 个臂（20/25/30/35/40/45/50 秒），线上持续试错学习各段用户的最优延迟。公式与 reward 定义由算法同学制定，我负责后端工程化。

#### 后端工程化方案

分桶：按付费等级分 HIGH/MID/LOW 三段独立统计（VIP/SVIP→HIGH、NP→MID、其他→LOW），段间隔离避免高价值用户被探索期稀释。选臂：UCB1（均值 + alpha·sqrt(ln N/n)），冷启动臂（次数<3）优先探索保证新档位曝光；选臂接口纯函数化，策略可离线单测。结算：reward = ln(成交卡片总价+1)，由支付/挂断回调异步结算，Lua 脚本原子执行（查 pending → 判提前支付 → 累加臂统计 → 清 pending），防支付回调与过期清理并发双结算；过期未结算 pending 定时批量清理，保证统计窗口无脏数据。配置：modelVersion（统计版本，改版本=统计重置）、臂列表、alpha、冷启动次数、价格表全量 Apollo/实验参数下发，后端不做决策只执行配置。存储：独立 Redis DB 物理隔离，不影响主链路。

#### 职责边界表述

算法同学定义怎么选（公式与 reward），我保证选的依据是准的（统计正确性、及时结算、脏数据清理）和策略可配置可回滚（参数化）。

### 1.4 可视化平台 Kafka 消费与查询链路优化

#### 背景与问题

可视化平台是推荐引擎的"行车记录仪"：线上引擎每次推荐把全链路执行过程（每个算子的候选明细、耗时、过滤原因）发到 Kafka debug topic，平台消费落库 MySQL 供算法同学回放排查。一次推荐 = 1 条消息 = 上千行候选明细。旧消费逻辑是逐行单条 INSERT（外层批、内层单插的假批量），落库后还在消费线程里同步逐条转发 Hive topic——消费线程被 DB 和 Kafka 两头 IO 串行拖住，高峰期 consumer lag 持续上涨，排障数据延迟几小时。

#### 方案与结果

吞吐：同 poll 批内合并明细按 500 条/块批量 INSERT，Hive 回写移出消费线程（异步线程池 + 200 条批量 send + linger.ms 聚合，失败重试 3 次），吞吐提升数倍。可靠性两个洞：部分落库失败仍提交 offset（静默丢数）→ 改为子批异常整批不 ack 重投，DuplicateKey 视为幂等成功；运维开关原设计"跳过落库但 ack"→ 改为 pause/resume 消费容器，offset 不动、恢复后原位继续——宁可 lag 堆积不丢数据。查询：历史列表 N+1（一页 10 条查 20 次 DB）改 2 次 IN 批量查询；simulate 接口去掉服务端 15 秒轮询（HTTP 线程全程阻塞），改为立即返回 + 前端短轮询 + 落库事件触发可视化。

#### 常见追问

这条优化有 commit hash 可查（个人分支 5e8b42d/053c12f/f5a7892）。pause/resume 的代价是维护期 lag 上涨——预期现象且可接受，数据丢了不会回来。

### 1.5 实验策略 Agent 开发

#### 背景与问题

策略实验的评估流程原来是纯人工：手动选参 → 跑 Hive SQL → 手工导 Excel → 手写飞书过程记录，一次实验评估半天起步。我先做了批量跑批平台解决"执行慢"（多线程跑批 + 异步飞书记录，端到端耗时降约 89%；定时任务动态调度，改 cron 不重启生效），在此基础上把"取数"这一步交给 Agent——构建知识库让 AI 按自然语言需求自助生成实验取数 SQL。

#### 方案

执行层：双线程池分工——跑批执行池（Abort 策略，池满快速失败保护下游 Hive 平台）、全局 SQL 队列池（CallerRuns 背压，不丢提交）；多线程批量跑 SQL + 异步写飞书过程记录，端到端耗时降约 89%。调度层：定时任务 cron 存 MySQL，ThreadPoolTaskScheduler + CronTrigger 动态注册/重载——页面改周期配置不重启即生效，含防重入与错峰补偿（重启后错过周期立即补跑）。知识层：两套知识库——业务表知识库（每张表一份文档：DDL/字段口径/参考 SQL，LLM 归纳 summary 向量化，按需检索）与指标口径与查询规范库（指标计算公式、日期参数约定、实验参数格式、常见问法转述，作为常驻提示词不走检索，保证每次生成口径一致）；Agent 生成 SQL 前检索 top-k 命中文档组装上下文，生成后直查内部 Hive 试跑验证。

#### 质量评估（三指标）

真实业务需求准确率：30~50 条真实历史取数需求 + 业务方核实过的结果数据，生成 SQL 直查比对结果集判卷；知识库外查询拒绝率：越界问题（未入库表/虚构指标）必须明确拒答——编造的 SQL 能跑的话错数据比报错危险；线上采纳率：生成的 SQL 被直接用/小改后用的比例。badcase 回流：每次人工修正把用户说法补进文档 summary 或转述表，同类错误只犯一次。

#### 常见追问

模型与规模：向量服务底层 bge-large-zh（约 3.3 亿参数、1024 维），知识库约 200 份文档 200 条向量 800KB，numpy 暴力余弦检索（零点几毫秒精确解）——规模小是特性不是缺陷，知识结构化是主体，向量检索是最薄一层；文档到万级再换 FAISS，由实测延迟触发升级。

## 二、项目经历：Seckill 商铺秒杀系统

---

### 2.1 项目定位

个人项目，完整实现秒杀的两条链路和一条补偿链路：券详情查询（读，练多级缓存）、优惠券秒杀（写，练削峰与一致性）、支付与超时取消（练状态机）。Docker Compose 七容器编排（Nginx 轮询 + 双 app 实例 + 四中间件），每个设计决策都有压测数字或对账结果支撑，全部可复现。

---

### 2.2 读链路：多级缓存

布隆过滤器是自研的 Redis Bitmap 实现：Murmur3 finalizer 混合 + Kirsch-Mitzenmacher 增强双哈希（一次 64 位哈希派生 k 个哈希位），位数组大小和哈希个数按标准公式推导（m = -n·ln(p)/(ln2)²）。读写分离贯通到过滤器内部：启动时从从库加载整个 Bitmap 为本地 BitSet，查询零网络往返；写入走主库 pipeline 合并 k 次 setbit。链路：布隆拦截不存在 id → L1 Caffeine（5s TTL，命中即微秒级返回）→ L2 Redis 从库（30min，轮询从库/失败回退主库）→ MySQL（SETNX 互斥锁重建 + 空值缓存差值化 TTL 防击穿/穿透）。压测：直连 MySQL 2.8 万 QPS → 多级缓存 590 万 QPS、P99 698µs → 1µs（口径说明：L1 命中是本地内存读，这个数字证明热 key 不走网络的设计生效，不是系统能扛 590 万并发）。

---

### 2.3 写链路：秒杀与最终一致性

写链路四层：令牌桶限流（容量 200/补充速率可配，惰性补充无后台线程；50 万突发灌入实测通过数与理论公式精确吻合，证明容量封顶、补充速率、拒绝路径三项实现均正确）→ Redis Lua 原子判定（一人一单去重 + 库存判断 + 扣减一次往返，并发下不可能超卖）→ Outbox 本地消息表（先 INSERT IGNORE 落账再发 Kafka，消除"Redis 已扣减但消息未发出"的崩溃窗口；落账失败调 Lua 幂等回滚 Redis 整体拒单）→ Kafka（acks=all + 幂等 producer）异步削峰，判定吞吐较纯 DB 乐观扣减 +146%。消费端：手动 commitSync + earliest 重放（宁重放不丢），INSERT IGNORE + 唯一索引幂等；消费失败重试 3 次转死信 topic 留痕，毒消息不卡分区。压测对账：混合压测后逐券校验 redis余量 + 生效订单数 = 1000，1000/1000 全部通过、零超卖——QPS 证明快，对账证明对。

---

### 2.4 多实例适配与状态机

状态机：支付 CAS 流转（0 待支付 → 1 已支付 / 2 超时取消），未支付订单挂 Redis ZSet 延迟队列，500ms 定时扫描到期取消，DB 回补 + Redis Lua 幂等回补（SREM 成功才 INCR，重复调用不多加），取消后可重新参与；支付成功主动移出队列。多实例适配：Nginx 轮询负载均衡（max_fails 摘除 + next_upstream 重试）；topic 显式双分区让双实例分组并行消费；超时取消扫描经 Redis 分布式锁互斥（锁短于扫描周期，实例崩溃自动接管）；雪花算法分布式 ID（workerId 环境注入）解决双实例订单号撞号，时钟回拨拒发；券详情缓存跨实例失效——更新走先更 DB → 删 L2 → pub/sub 广播踢各实例 L1，pub/sub 至多一次，丢消息退化为 5s TTL 兜底，实测更新即读新值。

### 2.5 已知边界（主动承认）

Redis 不持久化且无 DB 重建逻辑（重启后库存/去重集合丢失）；令牌桶单机内存态（集群限流 = 单实例 × 实例数）；590 万 QPS 是组件级数字，端到端 JMeter 实测 5338 req/s 零错误——两层口径不可比。
