# 实验策略与语音匹配服务——简历项目详细描述

本文档是实习经历各条目的完整展开：每条补充背景与问题、技术方案、以及高频面试问题的标准回答。

## 一、定位卡等待弹窗推荐

### 1.1 背景与问题

定位卡（cardType=8）用户的匹配成功率低于其他功能卡：用户用卡发起匹配后干等系统自然匹配，接通率随等待时间下降。业务方案是等待超过阈值（25 秒，Apollo 可配）仍无结果时，主动向等待用户弹窗推荐一个候选女性，把"干等"转化为"可接起的选项"。技术上要解决三个问题：多实例下弹窗任务如何不重复消费；候选如何不被并发流程抢占（锁定双方）；弹窗如何防止对同一用户反复骚扰（频控）。

### 1.2 技术方案

触发与排队：达到阈值时任务写入 Redis ZSet 延迟队列（score = 到期时间戳），多实例定时任务消费。消费采用 Lua 脚本原子弹出——ZRANGEBYSCORE + ZREM 在 Redis 单线程内一次往返完成，规避多实例重复消费；按具体 member 删除而非按分数范围删除，规避同分任务误删。

候选锁定：匹配执行前用 Redis 分布式锁锁定双方——SET NX EX 原子加锁杜绝"加锁成功但未设过期"的锁泄漏（进程崩溃后锁永久残留、用户无法再被匹配），释放时 Lua 脚本校验锁归属（是自己的锁才 DEL）防误删。

跨服务频控：弹窗发送（card_pop_sent）与曝光（card_pop_expose）双 Redis key 由 reco 服务写入、link 管线前置读取，实现主叫拦截与候选过滤——同一用户不会被反复弹窗。等待阈值与准入条件全量 Apollo 动态下发。

### 1.3 高频追问与标准回答

问：为什么用 ZSet 不用 Kafka 延迟消息？
答：弹窗触发是固定时长语义，ZSet 的 score 即截止时间，按分数范围取数天然匹配；且任务在 ZSet 里暂停消费不丢失、可人工查看。Kafka 做延迟要靠多层 topic 转储，复杂度不匹配。

问：锁为什么不用 Redisson？
答：这把锁是秒级互斥优化不是资金安全，SET NX EX + Lua 释放足够；Redisson 的看门狗、重试机制对几秒的预订锁是过度设计，少一个依赖。

问：锁过期了任务还没执行完怎么办？
答：锁的语义是减少冲突不是绝对正确，冲突场景下游有幂等；关键动作（弹窗发送）有频控 key 去重，双发也会被拦截。

## 二、超级匹配延迟弹窗

### 2.1 背景与问题

超级匹配是付费玩法：用户购买后系统延迟一段时间推送一个高质量候选。核心矛盾：热门候选（高价值女性用户）是稀缺资源，会被多个并发匹配流程争抢；且延迟期间锁可能过期、用户可能中途余额不足。要保证：用户买到手的弹窗，点过去对方确实是"为我预留的"。

### 2.2 技术方案

延迟队列闭环：Redis ZSet 延迟队列（score = 触发时刻），入队时顺手清理 5 分钟前的过期任务防止脏数据堆积；消费用 Lua 脚本原子批量弹出（取 + 删单次往返，多实例不重复消费）；弹出任务逐条提交独立线程池并发执行推荐——积压越深单轮弹出越多，消化速度自适应。批量大小与消费开关经 Apollo 动态下发：积压暴涨调大批量、下游过载关开关止血（任务持久在 ZSet 不丢，恢复后继续消化）。

提前锁定付费候选：推荐前置存在性预检（已被预订的候选直接跳过省一次计算）+ 分布式锁双向预订目标用户（SET NX EX 原子加锁）+ 延迟期间 TTL 续期（防预订比锁先过期）+ 结束时 Lua 校验归属释放。锁冲突自动跳过换下一候选，另有实验开关控制"预订失败是否放行继续匹配"（严格/宽松预订的业务权衡）。

策略路由与召回治理：余额检查结果路由两套策略管线（充足走正常推荐、不足走引流降级编排）；召回白名单双语义——调试场景只保留白名单候选（定向验证），生产场景剔除内部账号（防测试账号推给真实用户）。

### 2.3 高频追问与标准回答

问：延迟期间锁过期、人被别的流程抢走了怎么办？
答：延迟档位与锁 TTL 对齐配置，超长档位有双方续期；极端情况真被抢走，弹窗发送前还有频控与状态复查，最坏是推荐了竞争失败的候选，不产生资金损失。

问：为什么不改成数据库行锁保证绝对可靠？
答：候选是 Redis 池化数据不在 DB；锁是秒级预订优化，DB 行锁长事务代价远超收益。正确性底线由"频控去重 + 支付幂等"守住，锁只负责体验层互斥。

## 三、可视化平台 Kafka 消费与查询链路优化

### 3.1 背景与问题

可视化平台是推荐引擎的"行车记录仪"：线上引擎每次推荐把全链路执行过程发到 Kafka debug topic（一次推荐 = 1 条消息 = 上千行候选算子明细），平台消费落库 MySQL 供算法同学回放排查。三个问题：① 消费是逐行单条 INSERT + 同步逐条转发 Hive topic，消费线程被两头 IO 串行拖住，高峰期 consumer lag 持续上涨，排障数据延迟几小时；② 部分落库失败照样提交 offset、运维开关"跳过落库但 ack"——两处静默丢数；③ 查询接口在 HTTP 线程里轮询等数据落库（最长 15 秒），高并发时 Tomcat 线程被占满。

### 3.2 技术方案

吞吐：同一 poll 批内的明细合并按 500 条/块批量 INSERT；Hive 回写整体移出消费线程（异步线程池 + 200 条批量 send + linger.ms 聚合，失败重试 3 次）。

可靠性：子批失败异常向上抛、整批不 ack 触发重投，DuplicateKeyException 视为幂等成功——at-least-once + 幂等键去重；运维暂停从"跳过落库仍 ack"改为 pause/resume 消费容器，offset 不动、恢复后原位继续——宁可 lag 堆积不丢数据。

查询：simulate 接口 Dubbo 调完立即返回 requestId（HTTP 线程释放）；可视化计划改由落库事件触发（消息里本就带全链路数据，不再轮询 DB 等它）；历史列表 N+1 改 2 次 IN 批量查询 + 内存组装；双重 JSON 序列化改对象直转。

### 3.3 结果与标准回答

消费吞吐提升数倍、lag 高峰归零、恢复实时排障定位。

标准回答（异步 Hive 回写崩溃丢数据怎么办）：Hive 明细是离线分析旁路非资产数据，3 次重试覆盖网络抖动，极端丢失从 MySQL 事实源离线补偿——主链路 at-least-once 精确保障、旁路尽力而为可补偿，是刻意的成本分层。

标准回答（pause/resume 的代价）：维护期 lag 上涨是预期现象且会消化——止血手段本身不能成为新的故障源。

## 四、实验策略 Agent 开发

### 4.1 背景与问题

策略实验评估原来纯人工：选参 → 跑 Hive SQL → 导 Excel → 手写飞书记录，一次评估半天。分两步解决：先做批量跑批平台解决"执行慢"，再让 AI Agent 接管"取数"——按自然语言需求自助生成实验取数 SQL。

### 4.2 技术方案

平台层：双线程池分工（跑批执行池 Abort 快速失败保护 Hive 平台 / 全局 SQL 队列池 CallerRuns 背压不丢提交）；多线程批量跑 SQL + 异步写飞书，端到端耗时降约 89%；定时任务 cron 存 MySQL + ThreadPoolTaskScheduler 动态注册/重载，改周期不重启生效，含防重入与错峰补偿。

知识库（两套，职责分离）：业务表知识库——每张表一份文档（DDL/字段口径/参考 SQL），GLM 归纳 summary 向量化（内部向量服务，bge-large-zh 1024 维），按需 top-k 检索；指标口径与查询规范库——指标计算公式、日期参数约定、实验参数格式、常见问法转述，作为常驻提示词不走检索（全局标准不能依赖某次检索是否命中，否则口径漂移）。两库约 200 份文档 200 条向量 800KB，SQLite 存储 + numpy 暴力余弦（0.1ms 级精确解）——规模决定选型，万级再演进 FAISS。

生成链路：自然语言需求 → 归一化（话语转述表）→ 向量检索 top-k 文档 → 加载全文组装上下文（常驻规范 + 命中文档）→ GLM 生成 SQL → 直查内部 Hive EXPLAIN + 试跑验证。

### 4.3 质量评估与标准回答

评测集：50 条真实历史取数需求，标准答案 = 业务方核实过的历史结果数据（跳过 gold SQL 标注，直接以结果判卷），另含 20 条知识库外越界问题。

指标与实测：真实业务需求准确率 90%（45/50，错误复盘集中于复杂 JOIN 与时间窗口，属模型推理类残余）；知识库外查询拒绝率 95%（19/20 越界样本正确拒答——宁拒不编造，编出来的 SQL 能跑的话错数据比报错危险）；badcase 回流——每次人工修正把用户说法补进 summary 或转述表，同类错误不二犯。

标准回答（为什么不是 100%）：错误四类归因——检索漏（改 summary 可归零）、知识过时（挂变更流程）、模型推理错（规则压缩 + 验证兜底，占两成，是 90% 天花板的原因）、需求超覆盖（正确拒绝并收集为新文档）。

标准回答（k 怎么选）：k=5 + 相似度分数下限，200 份文档的小库让权衡简单——漏与噪在 k=5 达到平衡，评测集回归验证；top-1 都不达标则明确拒答。

标准回答（为什么不用向量数据库）：200 条向量 800KB，numpy 暴力余弦零点几毫秒且是精确解；ANN 是百万级的方案，为 200 条数据引索引构建与调参是负收益——选型跟规模走。
