# 项目三 · 四个故障场景的标准答案（对照实现 + 缺口与改进）

> 问题记录：
> ① Lua 成功了，但写消息（Outbox 落账）失败了怎么办？
> ② Lua 内部有些操作失败了怎么办？
> ③ 写消息成功，但 Kafka 生产失败怎么办？
> ④ 生产成功，但消费失败怎么办？

---

## ① Lua 成功、Outbox 落账失败

**本项目的处理**：`seckill()` 里落账失败向上抛异常，catch 后立即调用 `rollback(voucherId, userId)`——幂等回滚 Lua（`SREM` 成功才 `INCR`，把库存加回去、去重集合移除），返回 `DB_ERROR`，用户看到失败可立即重试。

**标准答案**：两个方向二选一——
- **补偿回滚**（本项目方案）：反向操作恢复现场，用户侧重试。优点是同步得到确定结果；缺点是回滚本身也可能失败（Redis 挂了），需要重试/告警兜底。
- **正向提交**：不回滚，允许"Redis 已扣、消息暂缺"的中间态存在，靠**对账任务**扫出"扣了但没订单"的差异并补发消息。优点是不怕回滚失败；缺点是用户拿到 SUCCESS 但订单迟到。

**关键认知**：跨 Redis/MySQL 两个存储不存在原子提交，只能选"补偿回滚"或"最终一致 + 对账"，**没有第三种答案**。面试说出这个取舍比背方案更加分。

**缺口**：当前 rollback 若抛异常（Redis 不可用）会吞掉异常只返回 DB_ERROR，扣减悬空。改进：回滚失败落一张 `pending_rollback` 表由定时任务重试，或靠 audit 分段对账暴露后人工/自动修复。

## ② Lua 内部有些操作失败了怎么办

**先纠正一个常见误区**：Redis Lua 提供的是**原子性**（执行期间不插入其他命令），**不是事务回滚**——脚本执行到一半出错时，已执行的命令**不会撤销**（Redis 官方明确没有回滚）。

**本项目的处理**：让脚本**结构上不存在中途失败点**——
1. 全部是 O(1) 确定性命令（SISMEMBER/GET/DECR/SADD），无过期键淘汰、无 OOM 命令、无类型错乱（值只有我们写入的字符串数字）；
2. 唯一可能的"逻辑失败"（库存不足、重复购买）在脚本开头判断并直接 return 0，**失败路径不产生任何写操作**；
3. 写操作（DECR/SADD）只在确认全部条件满足后执行，且只有两条。

**标准答案**：三层防线——
- **设计层**：脚本只包含不会中途出错的命令，先判后写；
- **崩溃层**：Redis 进程崩溃：脚本要么整体没开始，要么已完整执行（单线程 + 内存），配合 AOF everysec 最多丢 1 秒——我们部署关了持久化（压测环境），生产必须开 AOF；
- **兜底层**：**脚本不设计成幂等就没有救**——若重放同一脚本会双扣（DECR 两次）。崩溃恢复后的重放一致性依赖消息不重复 + 分段对账发现差异。

**缺口**：极端场景（AOF 丢 1 秒）会出现 Redis 与 DB 库存漂移，当前靠 audit 暴露、无自动修复。改进：对账发现差异后以 DB 三段数据为准回写 Redis（DB 是对账基准）。

## ③ 落账成功、Kafka 生产失败怎么办

**本项目的处理**（这是 Outbox 模式的主场）：`sendReliably` 先 INSERT `tb_local_message`（status=0 PENDING），再异步 `producer.send()`：
- 发送成功 → 回调 `markSent`（带 sent_at）；
- 发送失败/回调失败 → **什么都不做**，消息保持 PENDING；
- `LocalMessageRelay` @Scheduled 每秒扫描 PENDING 重投（retry<10），成功标记 SENT。

**标准答案**：消息的"存在性"由 MySQL 事务保证（落账成功=消息一定存在），Kafka 只是投递通道，通道失败不影响消息本体。中继重投 + 消费端幂等 = **最终一致 + 至少一次**。这是 Transactional Outbox 的教科书场景，同类替代方案：RocketMQ 事务消息（半消息+回查）、Canal 订阅 binlog 变更直接产生消息（连中继扫描都省）。

**实测证据**：压测中 Kafka 正常时 pending=0（主路径秒级 markSent），sent_at 字段可观测投递延迟（积压期最长 124s，正常毫秒级）。

**缺口**：retry≥10 的消息进入"死状态"（不再重投也不告警）。改进：超限消息转死信标记 + 告警人工介入；或中继改用批量拉取提高重投吞吐。

## ④ 生产成功、消费失败怎么办

**本项目的处理**：
- 消费者 `enable.auto.commit=false` **手动提交**：一批消息全部处理完才 commit offset——处理失败不提交，下次 poll（或实例重启后）从已提交 offset **重放**；
- `auto.offset.reset=earliest`：group offset 丢失时从头重放，**宁可重复不丢**；
- 重放导致的重复消费由 `INSERT IGNORE` + `(voucher_id, user_id)` 唯一索引吸收（DB 层幂等），`lockStock` 只在插入成功后执行（代码里 `if (insertUnpaid > 0)`），重复消息不会二次扣减。

**标准答案**：Kafka 的交付语义由 offset 提交时机决定——
- 先处理后提交 = **at-least-once**（可能重复，需消费幂等）← 本项目选择
- 先提交后处理 = at-most-once（可能丢）——不可接受
- exactly-once = 事务 API / 幂等生产者 + 事务消费，成本高，一般用"至少一次 + 业务幂等"等效达成

所以标准句式是："**我们选择 at-least-once 语义，用消费端幂等把'至少一次'升华为'业务上的恰好一次'**"。

**已补齐（死信队列）**：`handleWithDlt` 对单条失败原地重试 3 次（瞬时故障自愈），仍失败则把消息投递到 `{topic}-dlt` 死信主题并放行 offset——毒消息（永久故障）不阻塞分区、不静默丢弃，可回溯可告警。

**实测演示**：`POST /admin/poison` 注入格式非法消息 `poison:not-a-number:xxx`，消费者重试 3 次后转运死信主题（日志 `[DLT] 重试 3 次仍失败... NumberFormatException`），`seckill-orders-dlt` 主题可查到该消息，随后正常抢券请求 SUCCESS 不受影响。

## 总结表（面试速答版）

| 场景 | 本项目方案 | 一句话原理 | 已知缺口 |
|---|---|---|---|
| ① Lua 成功、落账失败 | 同步补偿回滚 Redis，用户重试 | 跨存储无原子提交，只能补偿或对账 | 回滚自身失败无重试表 |
| ② Lua 内部失败 | 脚本设计为先判后写、无中途失败点 | Lua 是原子性不是回滚，失败路径不落写 | AOF 丢秒级数据时靠对账 |
| ③ 落账成功、生产失败 | Outbox PENDING + 中继每秒重投 | 消息存在性由 DB 保证，Kafka 只是通道 | retry 超限无死信告警 |
| ④ 生产成功、消费失败 | 手动提交 offset 重放 + INSERT IGNORE 幂等 + **DLT 死信队列（重试 3 次转运）** | at-least-once + 业务幂等 ≈ 恰好一次 | 死信目前仅落 topic，无自动告警 |

**统一底层思想**（面试收尾句）：四个场景的答案是同一件事——**不追求分布式原子性，而是让每一步失败后都可以安全地重做（幂等 + 补偿 + 对账），用最终一致换可用性**。
